## Project Overview

EnvManager is a comprehensive test environment management platform that enables organizations to model, track, book, and visualize their test environments across on-premise and cloud infrastructure.

**Core Capabilities**:
- Environment inventory and booking system with multi-project coordination
- Change management with approval workflows
- Release management with test phases (SIT, UAT, Staging)
- CI/CD deployment tracking and DORA metrics
- Infrastructure topology visualization from GitHub repositories (Terraform, Docker Compose)
- Multi-tenant architecture with data isolation

## Architectural Rules & Patterns

### 1. Multi-Tier Architecture

```
┌─────────────────────────────────────────────────────┐
│                    Frontend (React)                  │
│  - Pages, Components, Redux Store, API Services     │
└─────────────────────┬───────────────────────────────┘
                      │ HTTP/REST
┌─────────────────────▼───────────────────────────────┐
│              API Layer (FastAPI)                     │
│  - Endpoints, Request/Response validation (Pydantic)│
└─────────────────────┬───────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────┐
│            Service Layer (Business Logic)            │
│  - Domain logic, orchestration, validation          │
└─────────────┬───────────────────┬───────────────────┘
              │                   │
┌─────────────▼─────────┐  ┌─────▼──────────────────┐
│  Database Layer       │  │  External Services     │
│  - Models (SQLAlchemy)│  │  - GitHub, Jira, CI/CD │
│  - Repositories       │  │  - Neo4j, Redis        │
└───────────────────────┘  └────────────────────────┘
```

### 2. Backend Layer Responsibilities

#### API Layer (`backend/app/api/v1/`)
- **Purpose**: HTTP endpoint definitions, request/response handling
- **Rules**:
  - Use Pydantic models for request/response validation
  - Keep endpoints thin - delegate to service layer
  - Handle HTTP-specific concerns (status codes, headers)
  - Apply authentication/authorization decorators
  - Return consistent response formats
- **Example**: `environments.py`, `bookings.py`, `auth.py`

#### Service Layer (`backend/app/services/`)
- **Purpose**: Business logic, orchestration, domain rules
- **Rules**:
  - No HTTP-specific code (no Request/Response objects)
  - Coordinate between multiple repositories/models
  - Implement business validation rules
  - Publish domain events
  - Handle transactions
  - Reusable across different API endpoints
- **Example**: `booking_service.py`, `environment_service.py`

#### Database Layer (`backend/app/db/models/`)
- **Purpose**: Data persistence, ORM models
- **Rules**:
  - SQLAlchemy models with type hints (Mapped[])
  - Relationships defined with `relationship()`
  - No business logic in models (only data structure)
  - Use Base class for common fields (id, created_at, updated_at)
  - Migrations managed by Alembic
- **Example**: `user.py`, `environment.py`, `booking.py`

### 3. Multi-Tenancy Pattern

**Every tenant-scoped table MUST**:
- Include `tenant_id: Mapped[int] = mapped_column(ForeignKey("tenant.id"), nullable=False, index=True)`
- Filter by tenant_id in all queries
- Include tenant context in JWT tokens
- Enforce row-level security (PostgreSQL RLS policies in Phase 1)

**Tenant Context Flow**:
1. User authenticates → JWT token includes `tenant_id`
2. API endpoint extracts `tenant_id` from token
3. Service layer filters all queries by `tenant_id`
4. Database enforces RLS policies as additional safeguard

### 4. Event-Driven Architecture

**Outbox Pattern**:
```python
# In service layer, within transaction:
async with db.begin():
    # 1. Perform business operation
    booking = await create_booking(...)
    
    # 2. Write event to event_log table (same transaction)
    event = Event(
        event_type="BookingCreated",
        aggregate_id=booking.id,
        payload={...}
    )
    db.add(event)
    
# 3. Background worker reads event_log and publishes to RabbitMQ
# 4. Event consumers update Neo4j, send notifications, etc.
```

**Event Consumers** (`backend/app/workers/`):
- Neo4j sync consumer (update topology graph)
- Notification consumer (email, Slack, Teams, webhooks)
- Metrics consumer (update reporting tables)

### 5. Database Design Patterns

#### JSONB for Flexibility
- Use JSONB columns for:
  - Custom fields (user-defined metadata)
  - Configuration data (varies by component type)
  - Notification preferences
  - Settings and options
- Index JSONB columns with GIN indexes for query performance

#### Soft Deletes
- All entities use `deleted_at: Mapped[Optional[datetime]]`
- Never hard delete records (audit trail requirement)
- Filter `deleted_at IS NULL` in queries

#### Audit Trail
- Base model includes `created_at` and `updated_at`
- Change history tables track field-level changes
- Event log provides complete audit trail

### 6. Frontend Architecture

#### State Management (Redux Toolkit)
```
frontend/src/store/
├── index.ts              # Store configuration
├── authSlice.ts          # Authentication state
├── environmentSlice.ts   # Environment state
├── bookingSlice.ts       # Booking state
└── ...
```

**Rules**:
- Use Redux Toolkit's `createSlice` and `createAsyncThunk`
- API calls in async thunks, not in components
- Normalize state shape (avoid nested data)
- Use selectors for derived state

#### Component Structure
```
frontend/src/
├── components/           # Reusable components
│   ├── BookingCalendar.tsx
│   ├── ComponentConfigEditor.tsx
│   └── ...
├── pages/               # Page-level components
│   ├── Dashboard.tsx
│   ├── EnvironmentList.tsx
│   └── ...
├── services/            # API client services
│   ├── api.ts          # Axios instance
│   ├── authService.ts
│   └── environmentService.ts
└── types/              # TypeScript type definitions
```

**Rules**:
- Pages compose components
- Components are presentational (receive props)
- API calls in service layer, not components
- Use TypeScript interfaces for all props

### 7. GitHub-First Infrastructure Discovery

**Workflow**:
1. System entity links to GitHub repository (`github_repository_url`)
2. Background worker scans repository for:
   - Terraform files: `*.tf`, `*.tfstate`
   - Docker Compose files: `docker-compose.yml`, `docker-compose.*.yml`
3. Parsers extract infrastructure components:
   - Terraform → AWS/Azure/GCP resources
   - Docker Compose → containerized services
4. Components stored in PostgreSQL with source traceability
5. Topology projected to Neo4j for graph queries
6. Drift detection compares `.tf` vs `.tfstate`

**Fallback**: Manual file upload for systems without GitHub integration

### 8. API Design Standards

#### RESTful Conventions
- `GET /api/v1/environments` - List (with pagination, filtering)
- `GET /api/v1/environments/{id}` - Get single
- `POST /api/v1/environments` - Create
- `PUT /api/v1/environments/{id}` - Update (full)
- `PATCH /api/v1/environments/{id}` - Partial update
- `DELETE /api/v1/environments/{id}` - Soft delete

#### Response Format
```json
{
  "data": { ... },           // Single resource
  "items": [ ... ],          // List of resources
  "total": 100,              // Total count (for pagination)
  "page": 1,
  "page_size": 50
}
```

#### Error Format
```json
{
  "detail": "Error message",
  "error_code": "BOOKING_CONFLICT",
  "context": { ... }
}
```

### Creating a New Feature

**Example: Adding a new entity (e.g., "Release")**

1. **Database Model** (`backend/app/db/models/release.py`):
   ```python
   class Release(Base):
       __tablename__ = "release"
       tenant_id: Mapped[int] = mapped_column(ForeignKey("tenant.id"), ...)
       name: Mapped[str] = mapped_column(String(255), ...)
       # ... other fields
   ```

2. **Alembic Migration**:
   ```bash
   cd backend
   alembic revision --autogenerate -m "Add release table"
   alembic upgrade head
   ```

3. **Service Layer** (`backend/app/services/release_service.py`):
   ```python
   class ReleaseService:
       async def create_release(self, tenant_id: int, data: dict):
           # Business logic here
           pass
   ```

4. **API Endpoints** (`backend/app/api/v1/releases.py`):
   ```python
   @router.post("/releases")
   async def create_release(request: ReleaseCreate, db: AsyncSession):
       service = ReleaseService(db)
       return await service.create_release(...)
   ```

5. **Frontend Service** (`frontend/src/services/releaseService.ts`):
   ```typescript
   export const createRelease = async (data: ReleaseCreate) => {
       return api.post('/api/v1/releases', data);
   };
   ```

6. **Redux Slice** (`frontend/src/store/releaseSlice.ts`):
   ```typescript
   export const createRelease = createAsyncThunk(
       'releases/create',
       async (data: ReleaseCreate) => {
           return await releaseService.createRelease(data);
       }
   );
   ```

7. **React Component** (`frontend/src/pages/ReleaseList.tsx`):

## Common Pitfalls to Avoid

1. **❌ Don't put business logic in API endpoints**
   - ✅ API endpoints should be thin, delegate to services

2. **❌ Don't forget tenant_id filtering**
   - ✅ Always filter by tenant_id in multi-tenant queries

3. **❌ Don't make API calls directly in React components**
   - ✅ Use Redux async thunks and service layer

4. **❌ Don't use synchronous database operations**
   - ✅ Always use async/await with AsyncSession

5. **❌ Don't hard delete records**
   - ✅ Use soft deletes with deleted_at timestamp

6. **❌ Don't skip migrations**
   - ✅ Always create Alembic migrations for schema changes

7. **❌ Don't store secrets in code**
   - ✅ Use environment variables and .env files
