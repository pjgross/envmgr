> **Sorting collates by byte value on every engine this app runs on**, which #39 fixed in the shared `apply_sort` by folding case explicitly. SQLite's default collation is `BINARY`, and the app's `postgres:15-alpine` uses **musl libc, which implements no locales** — the database reports `datcollate = en_US.utf8` while `SELECT 'a' < 'B'` is false. `docker-compose.prod.yml` only remaps ports, so **prod collated identically; this was never dev-only.** Do not "fix" ordering by changing the base image or the declared collation — keep it explicit in the query, as the NULL pinning already is. When testing a sort, assert **rendered row order over mixed-case data**: the pilot's assertions pinned the emitted SQL token and stayed green while the order users saw was wrong. > What C2 established, and what will bite if forgotten:
>
> - **C2 ADVISES; IT NEVER BLOCKS.** Fifth sub-project in this codebase whose central promise is a named test rather than an absence in the diff (after A3, A4, B2, B4).
> - **ONE EVALUATOR, TWO ROUTES.** `gate_readiness_service.evaluate()` is the only place the rules live; the release page's banner and the pipeline endpoint both call it, so a chip and the answer a pipeline obeys can never disagree.
> - **`webhooks:release` IS A NEW SCOPE, AND THERE IS STILL NO CANONICAL SERVER-SIDE SCOPE LIST.** `ApiKeyCreate.scopes` is a free-form `list[str]`; nothing validates a scope name against a whitelist, so a typo'd scope on a key is silently unusable — the key saves, the plaintext shows once, and every call 403s with no hint the typo is the cause. Found by Task 7's implementer as an environmental finding, not fixed here.
> - **EVIDENCE STALENESS IS COMPUTED ON READ AND KEYS ON `status == "success"` EXACTLY.** Evidence goes stale the moment a **later, successful** deployment of the same component into the same environment exists — a rolled-back or failed redeploy does **not** supersede anything, because it would be wrong to invalidate evidence that still correctly describes what is actually running. Nothing is stored; a stored flag would be falsified by the next deployment webhook.
> - **A WAIVER IS LIVE ALL THROUGH ITS EXPIRY DAY**, through `expiry_boundary` — the same rule A4's escalations and B2's grace periods follow, because the UI writes an expiry at `T00:00:00Z` and comparing at instant precision would read a waiver as expired from one minute past midnight on the day it was still meant to hold.
> - **`approved_by_username` must NOT be tenant-qualified** — under master-admin impersonation the approver can legitimately sit outside the gate's own tenant; a `User.tenant_id ==` join would render them as nobody. Same rule as A3's `acknowledged_by_username`, A4's `usernames_for`, and B5's `environment_decommission_service.usernames_for`.
> - **THE MUI GOTCHA THIS SUB-PROJECT'S FRONTEND HALF FOUND**: `<Select aria-label>` lands the accessible name on the **root** node, not on the `role="combobox"` element a query resolves to. `GatesTable`'s per-row gate-type `Select` uses `inputProps={{ 'aria-label': … }}` instead, which attaches it to the right node.
> - **ONE DEFECT THE TASK-11 BROWSER PASS FOUND AND FIXED, THAT A FULLY GREEN SUITE HAD MISSED**: the `gate_waived` readiness warning printed `f"Waived by user {id}."` — a raw database id, never resolved to a username, and never naming the expiry at all, contradicting the design's own rules table ("warning, naming approver and expiry"). No test had pinned the wrong text, only the warning's `type`. Fixed by reusing the already-batched, non-tenant-qualified `gate_waiver_service.usernames_for` inside the evaluator; two new tests pin a live waiver's detail (names the approver, states the expiry) and a permanent waiver's detail (says "no expiry" rather than printing a literal `None`).
> - **STILL API-ONLY, NOT REACHABLE THROUGH THE PRODUCT**: a release template's gate skeleton accepts `gate_type_id` on the backend (Task 6c), but the *Release Templates* admin page has no field to set it — only *Gate Name*, *Attach to Phase*, *Acceptance Criteria*. The SIT → UAT → Pre-Prod → Production strictness ladder §2.11 asks for therefore cannot be expressed through the UI today; every template-created gate starts untyped and has to be typed by hand on the release itself.

> What B6 established, and what will bite if forgotten:
>
> - **THE OVERLAP RULES ARE NOT RESTATED.** `conflict_service.conflicts_with` is the one definition of a clash; B6's `overlapping_pairs` calls it directly, making it the **fourth** consumer — after `list_conflicts`, `_unacknowledged_conflict_exists`, and A4's own `contention_service._pair_conflict_exists` (predating B6; the one the original count omitted). The new-booking dialog's `preview-conflicts` endpoint is NOT a consumer here — `booking_request_service.preview_conflicts` re-implements the overlap predicate inline instead of calling `conflicts_with`, a separate, pre-existing gap this count does not paper over. A calendar marker disagreeing with the Conflicts panel about whether a clash exists would be worse than no marker.
> - **"LIVE" IS `conflict_service.TERMINAL_STATES`, NOT `booking_states.INACTIVE_BOOKING_STATUSES`** — the same pair A4 had to keep apart. `conflict_service` counts a **draft** booking *as* a conflict, so a contended marker can appear on a booking nobody has submitted yet.
> - **THE COUNT IS OF CONTENTIONS (PAIRS), NEVER BOOKINGS.** Two clashing bookings are one contention; counting marked bookings would double every pair.
> - **ONLY ONE SIDE OF A PAIR NEED BE IN THE REQUESTED SET.** A booking shown in September can clash with one running August–October that the calendar never fetches. Requiring both sides in range would silently hide exactly the long-running bookings most likely to collide, indistinguishable from an absence of contention.
> - **THE HORIZON TESTS THE OVERLAP INTERVAL, NOT EITHER BOOKING'S OWN SPAN** — a pair that starts clashing in four months is not a contention in the next six weeks even if one booking begins tomorrow.
> - **THE HORIZON IS INDEPENDENT OF THE VISIBLE CALENDAR MONTH, AND THAT INDEPENDENCE IS THE WHOLE CLAIM.** `ContentionHorizon` takes no props and owns its own `?horizon_weeks=` URL param. Proved by mutation: wiring the fetch to FullCalendar's `datesSet` failed the independence test immediately and was reverted.
> - **FOLD PRECEDENCE IS `unowned → owned → decided`, MOST ACTIONABLE FIRST.** A4's `expired` folds to **`owned`**, not a fourth visual state — an overdue escalation still has a named owner who owes an answer. **Decided contentions still show**, because A4 moves nothing: two bookings in a `decided` contention are still genuinely overlapping until a human acts on the decision.
> - **`contention_state` is folded per response, after the page is fetched** — permanently unsortable (`BOOKING_SORTS` cannot whitelist it) and deliberately not filterable on `GET /bookings` at all, since `/contentions` is already the filtering surface and a second filter would need a second definition of the fold. Seventeenth member of docs/pagination.md's permanently-unsortable set.

> What B5 established, and what will bite if forgotten:
>
> - **B5 ACTS, NARROWLY — IT DOES NOT ADVISE.** Do not describe it the way A3/A4/B2/B4 are described. The guard is an absence-of-everything-else test, not an absence-of-action test: `test_b5_acts_only_where_it_says.py` pins the status write and the booking refusal as the two **permitted** changes and asserts nothing else moves.
> - **THE STATE IS COMPUTED, NEVER STORED.** No status column, no scheduler, nothing to invalidate. `state_predicate` (SQL) and `decommission_state` (Python) must reproduce the identical first-match-wins branch order — cancelled, then torn_down, then extension_requested, then warned (teardown date in the future), then due — or a worklist filter and a rendered chip disagree. **A DEADLINE IS A DAY**, through `expiry_boundary`: the teardown day itself still reads `warned`.
> - **THE BOOKING REFUSAL IS A DATE RULE, NOT A "DECOMMISSION EXISTS" RULE**, so granting an extension widens what is bookable with **no second write** — moving `scheduled_teardown_at` is the whole action. It lands on **five** write paths — three creates (`create_request`, `add_environment` — a create in disguise a grep-by-endpoint sweep misses, and the legacy `booking_service.create_booking`) plus **two** date-extending edits (`booking_request_service.update_standard_fields` **and** `booking_service.update_standard_fields`, the second found only by reading the code, not by grep, and shipped with zero test coverage until a reviewer commented it out and 90 tests across 4 files stayed green anyway). The **recurrence path checks the furthest occurrence, not the first** — a short first booking plus a recurrence rule would otherwise create children past teardown silently.
> - **ONE EXTENSION PER DECOMMISSION.** Granting one moves the teardown date and **clears nothing** — the extension block stays as the audit record, and the row falls through to `warned` on the new date because branch 3 stops matching, not because anything was wiped. A second request is refused, pointed at cancel-and-re-raise.
> - **TEARDOWN IS GATED ON ATTESTATIONS; THE 422 NAMES WHAT'S MISSING.** Only **active and required** steps gate. **Cancel** — open to the operations group or an Admin, like every action except requesting an extension, and always reachable by an Admin even where no team is assigned (B3b's degradation rule, carried over) — is the only escape hatch, since there is no edit path on a decommission, the same shape A4 established for a wrong or departed contention owner.
> - **HEALTH SAMPLES ARE DELIBERATELY NOT ACTIVITY.** Idle detection counts only a deployment or an overlapping (not merely started) booking; counting health heartbeats would hide precisely the monitored ghosts the feature exists to find. Threshold is `COALESCE(tier.idle_threshold_days, policy.idle_threshold_days)`; only active environments are judged and every other environment answers **false, never null**; an environment younger than its own threshold is never idle. **Idle detection defaults to OFF per tenant.**
> - **Deviations on record (§2.12):** no per-environment logins/traffic exist, so idle detection uses deployments + bookings instead (bookings stand in for "logins" imperfectly — a booked-but-unused environment still reads active); teardown does not return the environment to an "Available" status, because there is no such status in this model — it sets `DECOMMISSIONED` and leaves the calendar to humans; EnvManager holds no cloud credentials, so attestations record that a **human** backed up and tore down, not that the register did; **Idle ships derived, never a status value** — the same call B1 made for `reserved_now`.

> What B3a established, and what will bite if forgotten:
>
> - **`UserGroup` is deliberately generic, not an "OperationsTeam".** A1 is `Project` + members — also a container of users — and **must point at this primitive** rather than building a second membership model, or users are left asking which one to add someone to.

> - Group name uniqueness is enforced **in the service**, not by a partial unique index — inert on SQLite, same call as `environment_tier`.

> - **B4 ADVISES; IT NEVER BLOCKS AND IT NEVER PREEMPTS** — `tests/test_b4_advises_never_blocks.py` is the guard (a soft booking may be made over a hard one, `check_overlap` answers identically for both levels, a hard booking still transitions and is still editable, a contention decision still moves nothing). > - **RANK IS PRIMARY; PROTECTION ONLY BREAKS A TIE.** `_protection_breaks_tie` is consulted in `no_project`, `unranked` and `equal_rank` — **never** in `ranked`. A hard booking does not beat a higher-ranked project, and **an unknown level must never lose**: the tie-break fires only when exactly one side is known-hard, so the sentinel's last element is `None`, not `"soft"`. `OUTCOME_PROTECTED` is **the first outcome other than `ranked` that has a winner**, so `winner_booking_id != null` no longer implies `outcome == 'ranked'` — anything keying on that (A4's `composedVerdict` did) silently skips the new case. The UI names that winner in its own line (`X holds; Y gives way`) rather than reusing "X outranks Y", which would be false exactly where protection is doing the work.
> - **THE LEVEL LIVES ON THE REQUEST, NOT THE BOOKING**, so every member of an A2 group booking shares one value by construction and a group can never be half protected. Consequence: `BookingResponse.protection_level` cannot come from `model_validate(booking)` and is set explicitly in `_to_response`, and it is **required, not defaulted**, on `EnvBookingSummary` — the same guard `agreement_gap` has, for the same six-construction-sites reason.
> - **THE UNCHANGED-VALUE CARVE-OUT IS LOAD-BEARING.** Only Admin/RM (or a master admin) may *change* a level; anyone may *send* the inherited one, because the form shows a non-admin their level read-only and submits the whole form including it. A bare role check breaks the primary create journey for every Developer. Same call B2's name rule made: the permission guards a CHANGE, not a MENTION. An explicit `null` is a **422 for everyone**, Admin included.
> - **TWO AXES, CONSTANTLY CONFLATED: `exclusive_use_requested` asks "can anyone else be in here with me"; `protection_level` asks "can I be pushed out".** Neither refuses a booking through `create_request`. The standing asymmetry is **unchanged and still open**: legacy `POST /bookings/` 409s on an exclusive overlap while the modern multi-environment `create_request` does not, so "exclusive" means something different depending on which path made the booking.
> - **`protection_level` is the COLUMN; `protection` is the QUERY PARAM.** FastAPI drops an unknown param silently, so `?protection_level=` filters nothing while looking right. No-selection is an **omitted key**, spelled `any` client-side (never `all`, `buildParams`' own sentinel — fourth sub-project to hit it), and an empty `?protection=` is a 422. Sorting by it **forces the `booking_request` join even with no filter set**; without that a bare `?sort_by=protection_level` 500s instead of sorting. It is deliberately **not** a member of docs/pagination.md's permanently-unsortable set: it is a stored column, not a post-query computation.
> - **DURATION IS APPLIED BY RULE:** `addDuration` adds whole days as CALENDAR days and everything else as minutes, so a 14-day sprint from 09:00 stays at 09:00 across a spring-forward (the instant offset lands at **10:00**, not 08:00 — the plan's own note had the direction backwards). The preset fills the end date only while the user has not edited it, tracked through react-hook-form's dirty state rather than by comparing against the preset.
> - **A ZERO-LENGTH BOOKING OVERLAPS NOTHING, AND THE EDIT PATH WAS MAKING THEM.** `EditStandardFieldsDialog` rendered both bounds as `type="date"` and sliced the ISO string to 10 chars, so every save sent `00:00–00:00` — and overlap is `start < end AND end > start`, which a zero-length interval satisfies neither of. Fixed here (both fields, plus BookingDetail's add-environment pair) through one shared `toDateTimeLocal` in LOCAL time; a UTC slice would show 09:00Z as 09:00 to a reader whose clock says 10:00.
> - **Deviation on record:** §2.12 says "**preemptible** vs protected". Nothing preempts anything. Refusal, refusal-plus-preemption-record and auto-preemption were each considered and declined — see the spec. And **the all-hard degradation is documented, not a defect**: if every booking type is Protected the level stops discriminating and verdicts name no winner again, exactly as before B4.

>
> - **B2 ADVISES; IT NEVER BLOCKS A BOOKING** — `tests/test_b2_advises_never_blocks.py` is the guard (bookable, transitionable, still editable, still active), with `describe('B2 advises; it never blocks')` in `environmentCompliance.test.tsx` on the UI half. > - **The invalidation surface is exactly four write paths**: `create_environment_record`, `update_environment`, request fulfilment, and `upsert_policy` → `recompute_tenant` (whole tenant, inline, no scheduler). **The disable path matters as much as the enable path** — turning a policy off must return the estate to "no rule applies", not freeze the last judgement.
> - **`name_compliant IS NULL` means "no pattern applies" and counts as COMPLIANT**, never unknown and never failing. **The grid cell keys on the GAP LIST, never on the verdict**: a row can be in gap for a missing owner with `name_compliant` true, so a cell reading the verdict alone both misses real gaps and flags the whole estate of a tenant with no policy.
> - **`?governance_gap=` was deliberately NOT touched**, so two overlapping chips ship: *Governance gap* is B1/B3a's fixed pair (owner **or** operations group), *Policy gap* is whatever the tenant's policy asks. Folding one into the other would make an existing filter's meaning depend on tenant configuration.
> - **`tier` is deliberately absent from the vocabulary** (`environment.tier_id` is already `nullable=False`, so requiring it is a check that can never fail — B1 made it structurally mandatory, which is stronger) and is rejected **by name** rather than silently accepted. **No `non_compliant_since`, no `QUARANTINED` status**: an environment that breaks compliance later is quarantined at once with no fresh grace, and a quarantined environment is still **active**.

And `effective_from` bumps in **either** direction on a rule change (relaxations included — "stricter" is not decidable for a regex) but **not** for `grace_days`, `is_enabled` or the example.
> - **The ReDoS residual risk is stated, not solved.** PyPI `regex` (a syntax superset of `re`, with a per-match timeout) bounds **every** match — save-time check, every write, every row of a recompute; two earlier designs bounded only the policy save. Compilation is bounded separately (no timeout covers compilation) and the subject by `MAX_NAME_LENGTH`, checked inside `name_matches` because `excel_import_service` reaches `create_environment_record` with a spreadsheet cell and no Pydantic cap applies. **Not bounded:** a slow-but-finishing pattern, whose cost is paid on every write, and the budget is per *match* — N environments against a pathological pattern costs up to N × the timeout.
> - **Deviation on record:** §2.12 says "quarantine/**terminate**". B2 terminates nothing — a register holds no credentials to destroy a resource with, and no way to know the row still corresponds to anything running.

> What A4 established, and what will bite if forgotten:
>
> - **`test_a_contention_changes_no_booking_behaviour` is the guard on the whole design** (with `test_recording_a_decision_changes_nothing_on_either_booking` on the decision path, and `describe('A4 advises; it never acts')` in `ContentionVerdict.test.tsx` on the UI). **If any fails, A4 has started acting.** This is also *why* A2's group bookings needed no special case: an advisory verdict cannot tear a group apart, so the phase doc's "per environment or per group?" question is **dissolved, not answered**.
> - **NOTHING IS STORED BUT THE ESCALATION, and even its state is computed.** The verdict depends on two bookings *and* two project ranks — four edits could falsify a cache — and `open`/`answered`/`expired` follow from `respond_by` and `decided_at`. **There is no status column, no scheduler and nothing to invalidate.** Answering late is still `answered`; `state_predicate` reproduces that branch order in SQL so the worklist filter and the rendered rows cannot disagree. **A DEADLINE IS A DAY**: both compare `respond_by` against `expiry_boundary(now)` (the start of the current UTC day), because the UI writes it at `T00:00:00Z` — at instant precision an escalation read `expired` from one minute past midnight on its own deadline day, and `?state=open` therefore hid every contention due today. Same class as `formatExpiry`'s "overdue by 1 day", already in the pitfalls below.
> - **FOUR OUTCOMES, THREE WITH NO WINNER, FIVE REASONS.** `no_project` carries two, because a request naming an *unresolvable* project renders that project's NAME beside the verdict (`get_project_names` deliberately does not filter `deleted_at`), and "not linked to a project" then reads as a bug in the register. **A ranked project deliberately does NOT beat an unranked one** — unranked means "priority does not separate these", and treating it as lowest would have declared the whole existing estate the loser on day one.
> - **`_ranks_for` takes the project id from the tenant-filtered LEFT JOIN, never from `BookingRequest.project_id`.** Read it off the request and an archived or cross-tenant link reports as "has a project, and it is unranked" — so an admin is told to rank a project whose rank that same join then refuses to read, sets one, and watches nothing change.
> - **The rank is settable on both create and update**, though the *New Project* dialog has no rank field — `POST /projects` silently DISCARDED `priority_rank` until a browser pass caught it (`ProjectCreate` had neither the field nor `extra="forbid"`, the `POST /tenant/lifecycle-templates` silent-drop class), and both schemas now carry `extra="forbid"` + `ge=1`. `ProjectUpdate` keys on `model_fields_set`, so an omitted key means "leave alone" and only an explicit null unranks.
> - **One escalation per contention, keyed on the NORMALISED pair** (`uq_contention_pair`). Re-asking returns the existing record **unchanged** — 200, not 201 — and the supplied `owner_user_id`/`respond_by` are ignored, unlike the two ack upserts where the later answer wins: an escalation starts a clock against someone else, so either party could otherwise restart the other's. The existing record is looked for **before** the conflict check, so re-asking keeps working after the pair stops overlapping.
> - **Escalating is the owner or a delegate of EITHER booking, or an Admin; answering is the NAMED OWNER or an Admin.** There is **no edit and no withdraw path** — nothing anywhere sets `ContentionEscalation.deleted_at` — so **the Admin answer is the only escape hatch** from a wrong or departed owner. B3b shipped the opposite and produced two unrecoverable states. The frontend's `canEscalate` is deliberately *narrower* than the server's rule (subject side + Admin): the other booker gets the control on their own page.
> - **An escalation OUTLIVES its bookings**; `bookings_live` is computed and the worklist filters on none of it. "Live" is `conflict_service.TERMINAL_STATES` + `deleted_at`, **not** `booking_states.INACTIVE_BOOKING_STATUSES` — that set counts drafts as inactive while `conflict_service` counts them *as* conflicts.
> - **`usernames_for` must NOT be tenant-qualified** — A3's impersonation trap in batch form; `test_the_deciders_name_resolves_from_outside_the_escalations_tenant` fails with the join added. Every other name travels with the row too, resolved through the **read-rendering** lookups (`get_environment_names`/`get_project_names`/`get_group_names`), none of which filters `deleted_at`.
> - **The group name is part of what identifies a booking.** A decision naming one member of a group booking is a decision about every member (A2 transitions atomically), so the note renders **per row**, only where that side has a group — a blanket page-level hedge fires on the majority of rows that have none. **Consequence nobody is warned about:** two group bookings clashing on three environments produce three independent contentions and three independent decisions, and a set like "A yields on env1, B yields on env2" is mutually unsatisfiable. Recorded in the user guide; a cross-contention consistency check is a ticket, not a defect, since A4 advises and a human reconciles.
> - **`?state=`'s "no selection" is an OMITTED KEY**; there is deliberately no `all` value and the URL spells it `any`, for the `buildParams` sentinel reason. One clock per request decides both the filter and every rendered state.
> - **`GET /bookings/{id}/conflicts` now runs four A4 batches beside its existing three — and is still not fully batched**: `conflict_service.get_ack` remains one query per row (pre-existing, not A4's), and **`booking_labels` runs TWICE per page** — once from the endpoint and again inside `escalation_views` — so its three name lookups each run twice and `get_group_names` three times. Constant per page, not an N+1; both are disclosed in the code and ticketed rather than fixed, so the batching note there is not read as a claim about the endpoint.
> - **Deviation on record:** §2.12 says "escalation to the Release Manager"; A4 validates only that the named owner exists in the caller's active tenant — **no role check, and no `is_active` check** (a contention assigned to someone who has since left still names them).
> - **Out of scope by decision, now [issue #8](https://github.com/pjgross/envmgr/issues/8):** `DELETE /booking-requests/{id}/environments/{booking_id}` silently shrinks an atomic group booking — `remove_environment` never looks at `environment_group_id` and `_group_bookings` filters `deleted_at`, so the survivors transition and report success. API-only today (the UI passes only ungrouped bookings to the remove control). A2's defect, not A4's.

## Production Deployment

Production runs on **macmini** (Tailscale network). EnvManager's containers are deployed via docker-compose. Several infrastructure services are shared from the macmini host rather than duplicated.

```bash
SECRET_KEY=$(openssl rand -hex 32) POSTGRES_PASSWORD=... \
  docker compose -f docker-compose.yml -f docker-compose.prod.yml \
    --profile app up -d --build
```

- `backend` and `frontend` live under the compose **`app` profile** so the dev flow above (`docker-compose up -d` for infra, uvicorn + vite on the host) doesn't fight them for ports 8000/5173.
- `SECRET_KEY` and `POSTGRES_PASSWORD` are **required** — compose fails fast without them, and the backend refuses to start with `DEBUG=false` and the repo's placeholder key.
- **`SECRETS_ENCRYPTION_KEY`** is required once any tenant connects a third-party credential (today: GitHub). Generate with `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`. It is **deliberately not `SECRET_KEY`** — that one signs JWTs, and the two have different blast radii and rotation schedules. **Losing this key makes every stored credential unrecoverable**: nothing can decrypt them, and every tenant must reconnect. Rows carry a `key_version` so a future rotation can re-encrypt in place.
- **`GITHUB_OAUTH_CLIENT_ID`** is optional. Absent, the GitHub integration endpoints answer 503 with a clear message and nothing else is affected. It is the client id of an OAuth App used for the device flow, which needs no client secret.
- The backend image's entrypoint runs `alembic upgrade head` **before** uvicorn. That order matters: `init_db()` calls `create_all`, so if the app started first it would build the schema itself and leave `alembic_version` empty, after which migrations fail on "relation already exists". Set `RUN_MIGRATIONS=0` to skip.
- The frontend image is nginx serving the built bundle and proxying `/api` to `BACKEND_ORIGIN` (`src/services/api.ts` uses a relative `/api/v1` baseURL, so whatever serves the bundle must also proxy the API).
- Port lists in `docker-compose.prod.yml` use `!override`; without it compose **appends** to the base list and republishes the base port too.

## Adding a New Feature (checklist)

1. `backend/app/db/models/<entity>.py` — SQLAlchemy model with `tenant_id`; all enum columns use `native_enum=False` (stores as VARCHAR — keeps SQLite test compat)
2. `alembic revision -m "..."` then write DDL **manually** — do NOT use `--autogenerate` (init_db uses create_all so autogenerate sees nothing to do for new tables); use `op.create_table()` for new tables, `op.add_column()` for new columns
3. `alembic upgrade head`
4. `backend/app/services/<entity>_service.py` — business logic, no HTTP code; use `db.flush()` not `db.commit()` when you need the DB to assign an ID mid-transaction
5. `backend/app/api/v1/<entities>.py` — thin endpoints, delegate to service
6. `frontend/src/services/<entity>Service.ts` — API client
7. `frontend/src/store/<entity>Slice.ts` — Redux slice with async thunks
8. `frontend/src/pages/<EntityList>.tsx` — page component using Redux

## Common Pitfalls

- **Business logic in API endpoints** — keep endpoints thin, put logic in services
- **Missing tenant_id filter** — every query on tenant-scoped tables must filter by `tenant_id`; use `current_user.active_tenant_id` (not `.tenant_id`) to handle impersonation correctly
- **API calls in React components** — use Redux async thunks + service layer instead
- **Synchronous DB operations** — always use `async/await` with `AsyncSession`
- **Hard deleting records** — use soft deletes (`deleted_at = datetime.now(timezone.utc)`); only dependency/junction records use hard delete
- **Skipping migrations** — always create an Alembic migration for schema changes; write manual DDL (see checklist above)
- **`db.commit()` in services** — `get_db()` auto-commits on success; calling `db.commit()` inside a service will break the outbox pattern (event rows must commit atomically with the business write). Use `db.flush()` if you need the DB to assign an ID mid-transaction
- **Native enums** — always set `native_enum=False` on enum columns; PostgreSQL native ENUMs break SQLite-based tests and are hard to alter later
- **`--autogenerate` migrations** — `init_db()` calls `create_all`, so Alembic autogenerate sees tables as already existing and generates empty migrations. Always use `alembic revision -m "..."` and write the DDL manually
- **Fabricating foreign keys in tests** — never point a test row at an id you haven't created (`subsystem_id=1`, `raised_by=1`). SQLite silently ignored FKs until `PRAGMA foreign_keys=ON` was added, so ~40 tests were inserting broken rows and passing. Use the helpers in `backend/tests/factories.py`
- **Testing only on SQLite** — the suite defaults to in-memory SQLite, but partial unique indexes and other dialect-gated DDL are inert there. Run it against PostgreSQL too before trusting a schema or query change: `TEST_DATABASE_URL=postgresql+asyncpg://envmgr:envmgr_dev_password@localhost:5432/envmgr_test uv run pytest -q` (CI runs both legs)
- **Secrets in code** — use environment variables and `.env` files. `SECRET_KEY` must be set for any `DEBUG=false` deployment; the app refuses to start with the repo's placeholder
- **Self-service user creation** — there is no `/auth/register`; create users via `POST /api/v1/tenant/users`, which is admin-gated and forces the caller's tenant
- **Unbounded list endpoints** — new list endpoints take `page: Page = Depends(pagination())` (it's a factory — call it) and their service returns `(rows, total)` via `fetch_page` for a single-entity select or `fetch_page_rows` for a multi-column one; see [docs/pagination.md](docs/pagination.md). Order by a **unique** key — append the primary key as a tiebreaker, or `LIMIT`/`OFFSET` will duplicate and drop rows across pages once ties exist. Never add `limit` to an endpoint whose service filters in Python after the query, or merges two executed queries — the page would be windowed before the filter and the results quietly wrong. If the endpoint also needs a `sort_by`/`sort_dir`, use `sorting()` (same file) the same way: it's a **whitelist** mapping client field names to ORM columns — `sort_by` is never used to address a column directly (no `getattr`, no interpolation) — and an unknown `sort_by` is a **422**, not a silent fallback. Chain `apply_sort` **before** the tiebreaker, never instead of it (`apply_sort(query, sort).order_by(Model.id)`), and never whitelist a column a service computes in Python after the query — it isn't backed by a single column to sort by
- **Trusting the database's collation for text order** — `apply_sort` folds case itself (`lower(col)`) for `String` columns rather than letting `ORDER BY name` mean whatever the engine decides. Both engines here collate by **byte value**: SQLite's default is `BINARY`, and `postgres:15-alpine` runs musl libc, which implements no locales — the DB reports `en_US.utf8` but `SELECT 'a' < 'B'` is false, in prod as well as dev. Don't "fix" ordering by changing the image or the declared collation; keep it explicit in the query, the same way NULLs are pinned. When testing a sort, assert **rendered row order over mixed-case data** — an assertion on the emitted SQL string will stay green while users see the wrong order
- **Evaluating a tenant's regex anywhere but `environment_compliance_service.name_matches`** — the name verdict is stored precisely because no regex is portable across both engines. A second evaluator (PostgreSQL's `~`, a SQLite callback, or a JavaScript `RegExp` in an admin form) is a second opinion on one rule, and the two disagree on real patterns: a name refused at save then reports compliant in the list. The admin panel's "what would this do" preview goes through the **server** for this reason. Note the engine is PyPI **`regex`**, not `re` — `re` has no per-match timeout, and a tenant-authored pattern runs in a shared multi-tenant process; if you add a match anywhere, it must be that one function or it is unbounded
- **Minting tokens by hand** — `create_access_token` alone produces an unrevocable session. Use `auth_session_service.issue_session`; anything that invalidates a password must call `revoke_all_for_user`
- **Parsing that writes as it goes** — a scanner detector returns a `DeclaredState` value and touches no database. `reconcile.apply()` writes it, `reconcile.diff()` compares it, and both read the *same* value — which is what stops the drift report describing a change a scan would not make. `test_reconcile_roundtrip.py` asserts it (`apply` then `diff` == zero drift) and has already caught the two sides de-duplicating repeated edges in opposite directions. Truncate to column widths **in the parser, never in `apply()`** — otherwise a stored row differs from the declaration it came from and `diff()` reports a phantom change on every run. **SQLite does not enforce column widths at all**, so a dropped truncation fails only on the PostgreSQL leg
- **Treating a partial read as a complete one** — `GET /systems/{id}/github/drift` computes "in the catalogue but not in the code" only when the whole tree was read. A truncated tree, the file cap, an unread path or a fetch error each make an unread file indistinguishable from a deleted one, so the absence categories come back **`null` with a reason, never `[]`**, and the UI omits the group instead of rendering it empty. Watch this at *every* level: a summary computed from "categories that were computed" reads as a clean bill of health when in fact nothing could be checked — the drift dialog announced "the catalogue matches the code" directly above its own truncation warning until that was fixed
- **A new grid column whose `field` collides with a tenant custom-field key** — `buildCustomFieldColumns` used to emit `field: def.field_key`, so a tenant with a custom field keyed `owner` got two columns sharing one id the moment B1 added a static `owner` column. MUI then emitted a spurious visibility change that the page's own `saveColumnModel` persisted, **silently hiding the real column**. No test could catch it: no fixture defines a colliding custom field. Environment columns are namespaced `cf_<key>`; **`BookingList.tsx` and `SystemCatalog.tsx` were namespaced the same way on 2026-08-04**, each with a test asserting no custom-field column's `field` can collide with a static one and one asserting the valueGetter still reads the *raw* `field_key` (the namespace is a grid-column id only — a valueGetter that looked up `cf_x` would render a correctly-named, permanently-empty column). Note the fix cannot retroactively repair a stored visibility entry whose key was already shared
- **Reading an API error from `result.error.message` on a rejected RTK thunk** — Redux Toolkit's default `miniSerializeError` copies only `name`/`message`/`stack`/`code`, and a real Axios error's `.message` is the generic `"Request failed with status code 409"`. The server's `response.data.detail` is dropped, so the user sees an HTTP status instead of the reason. Use `rejectWithValue(formatApiError(err))` (`services/apiError.ts`). A test that rejects with a plain `Error` carrying the final text **passes while the app is broken** — mock an `AxiosError` shape instead. `BookingTypesPanel`, `ComponentTypesPanel` and `LifecycleTemplatesPanel` were converted on 2026-08-04 — `componentTypeSlice` and `bookingLifecycleSlice`'s mutating thunks now `rejectWithValue(formatApiError(err))` and the panels read `result.payload`. One gap deliberately left: `LifecycleTemplatesPanel`'s **Copy** button dispatches `copyLifecycleTemplate` without inspecting the result at all, so a refused copy still fails silently — a missing-error-handling bug, not a wrong-message one
- **Reading `exclusive_use_requested` and `protection_level` as one setting** — they are two axes and neither implies the other: exclusive use asks *can anyone else be in here with me*, protection asks *can I be pushed out*. Protection refuses nothing anywhere (B4 advises), and exclusive use only 409s on the **legacy** `POST /bookings/` path — the modern `create_request` does not, an asymmetry that is still open. A control, message or filter that conflates them will be wrong for whichever half it did not mean
- **Adding whole days by adding milliseconds** — `addDuration` (`frontend/src/utils/duration.ts`) adds a whole multiple of a day as CALENDAR days precisely because an instant offset drifts an hour across a DST boundary: 09:00 + 14 days as milliseconds reads **10:00** on the wall clock after a spring-forward. Sub-day durations are minutes. Same family as `formatExpiry` below and SP5a's per-date localization
- **Day arithmetic by flooring a millisecond delta** — `formatExpiry` did this and reported an environment "overdue by 1 day" throughout the whole day it actually expired, because the form writes expiries at `T00:00:00Z`. Difference **UTC calendar days** (`Date.UTC(y,m,d)` on both sides), and drive any colour threshold from the same delta as the label, or the two disagree for a day
- **Assuming `current_user.id` belongs to `current_user.active_tenant_id`** — under master-admin impersonation they differ, so an owner/FK validation scoped to the active tenant 404s. In the spreadsheet import that `HTTPException` escaped the per-row `except (ValueError, ValidationError)` and killed the **entire upload**. Nothing in the suite covers the impersonation dimension of imports
- **`alembic downgrade -1` on the dev database** — it steps back from whatever the *current* head is, not from your new revision, so it will happily drop a table you did not write. Doing this while testing a migration dropped `tenant_secret` and wiped the dev tenant's stored GitHub token. Check `alembic current` first, and prefer a scratch database (`tests/test_migration_schema_drift.py` builds one) for exercising up/down
- **Building a thing and connecting it to nothing** — B5 shipped this **four times**, each caught by a different accident and none by a test: `idle` computed and filterable but absent from the response schema; `decommission_state` heading the same way until the plan was amended; `initiateDecommission` defined in the Redux slice with **no caller anywhere**, so the decommission workflow could not be started from the product at all; and `environment_tier.idle_threshold_days` — a model column with no schema field and no service handling, leaving the per-tier override unsettable while `COALESCE(tier, tenant)` silently always chose the tenant default. Every piece worked in isolation; nothing joined them, and none of it failed a test because there was no caller to exercise. **The question that finds these is "what consumes this?", asked of every new field, thunk and column — not "does this pass?"**
- **Writing dialect date arithmetic for a per-row threshold** — B5's idle threshold (`COALESCE(tier.idle_threshold_days, policy.idle_threshold_days)`, one cutoff instant per distinct tier override) resolves `boundary - timedelta(days=...)` to a plain Python instant **once per request** and injects it as a literal inside a SQL `CASE` keyed on `tier_id`, rather than asking either engine's date functions (`interval` vs `datetime()`) to subtract days per row. The decommission state machine takes the same "resolve once, compare as a literal" shape but without the `CASE` — `expiry_boundary(now)` is one instant, compared directly (`scheduled_teardown_at >= boundary`). Both exist for the same reason `apply_sort`'s case-folding and NULL-pinning do: row-visible behaviour must not depend on which engine happens to be running underneath it, and SQLite's and PostgreSQL's date arithmetic do not agree closely enough to trust directly in a query
- **Reasoning about what a column comparison emits instead of compiling it** — B5's spec draft spent two rounds arguing that `Environment.status != "decommissioned"` was inert because the column stores `ACTIVE`/`DECOMMISSIONED`, not lowercase. **It is not inert** — SQLAlchemy's `Enum` coerces a value-matching string literal to the stored member name at compile time, so `Environment.status != "decommissioned"` and `Environment.status != EnvironmentStatus.DECOMMISSIONED` emit byte-identical SQL. One `compile(compile_kwargs={"literal_binds": True})` settles a question like this in seconds instead of another round of confident argument. **There is no status-literal bug anywhere in this codebase — do not go looking for one on the strength of this entry**
- **`conftest.py`'s `tenant` fixture is not an alias for `test_tenant`** — despite a docstring that used to say so. It creates a *different* tenant ("Phase3 Org" / `phase3-org`, versus `test_tenant`'s "Test Org" / `test-org`). A test that combines `tenant` with `auth_headers` (which authenticates into `test_tenant`) is querying across two tenants and **can pass vacuously** — found on B5 by an implementer who then used `test_tenant` instead; the docstring is now corrected. Service-level tests that use `tenant` consistently, with no HTTP/auth layer, are self-consistent and not at risk — the trap is only in mixing the two
- **Using `GREATEST`/`LEAST` for an interval test** — SQLite has neither. B6's overlap-interval filter (`contention_forecast_service.overlapping_pairs`) needs no dialect function at all: `max(a,b) < X` decomposes to `a < X AND b < X`, and `min(a,b) > Y` decomposes to `a > Y AND b > Y`. Reach for a dialect-specific function here and the query works on PostgreSQL and breaks on SQLite, or vice versa, for a comparison that never needed one
- **Registering a literal route after a `/{id}` catch-all** — `GET /{booking_id}` captures the literal path segment `contention-horizon` as if it were an id, and only fails at Pydantic's int coercion, so `GET /bookings/contention-horizon` 422s on every call regardless of its own query parameters, whatever they are. Found empirically in B6's TDD red run, not by reasoning about FastAPI's routing rules in advance. Literal-segment routes must be registered **before** the `/{id}` catch-all in the same router; `bookings.py` registers `/contention-horizon` ahead of `/{booking_id}` for exactly this reason, and a reviewer checked every other route in that router to confirm no sibling has the same bug
- **A pair normalisation that hides the filter it needs** — B6's `overlapping_pairs` normalises every result to `b1.id < b2.id`. In every hand-written test fixture the row meant to be *excluded* (wrong tenant, not live, soft-deleted) was created **after** the live one, so it always took the higher id and landed in the `b2` role — where `conflict_service.conflicts_with`'s own filter on `b2` already excludes it, whichever filter is on `b1` never fires, and the test still passes. Three of `b1`'s own compensating filters (`tenant_id`, `deleted_at`, liveness) were unguarded by any test this way, found only by mutation (dropping each filter and watching nothing fail). The general lesson: when a test's fixture is built to make a row excluded, check **which side of a normalised join or self-join it lands on** — a filter can be dead code in every test while still being live in production, or the other way round
- **Concluding a rule is untestable without building the probe** — B6's cross-tenant filter on `b1.tenant_id` was reasoned to be unreachable ("environment ids are globally unique, so a cross-tenant `b1` can never find a same-environment `b2`") and recorded as defence-in-depth, not a real guard. A later reviewer built the probe instead of accepting the reasoning: `make_booking`'s `tenant_id` and `environment` arguments are independent and uncross-checked, so a booking whose `tenant_id` is one tenant while its `environment` belongs to another is entirely constructible, and doing so found a **real cross-tenant isolation leak** the "unreachable" conclusion had waved past. An honest "not reachable" is a conclusion to verify by construction, not one to accept on the strength of a plausible argument — especially when someone was told that conclusion would be accepted, which is exactly the incentive that let the wrong one through the first time
